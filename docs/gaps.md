# Gaps

What umcfGui can't do yet, most important first. Work is picked from the top. A row is removed
in the same pull request that closes it.

## Next

The goal they lead to: a working case built in umcfGui from STL surfaces of its regions, with a
blockMesh background, its patches set up, its radiation and weather data set, and a mesh that can
be reset and made again. [What a case needs](case-requirements.md) is the specification, and
[the common workflow](common-workflow.md) the design rows 4–9 and 12 build.

## Known limits

| Limit | Effect | Possible fix |
|---|---|---|
| `Case::open` reads each start-time field file whole to list its boundary conditions | Opening a case at a late time with gzipped multi-GB fields takes 20 s (Hong Kong project: 30 fields, 4 GB; 9.4 s at its start time), the files read one after the other, and each `internalField`'s values parsed only to count them; files over 256 MB are listed without their BCs | Read the field files in parallel, of `internalField` only its kind and length (from the list's header; binary data passed over by its size) and `boundaryField` fully; the values only for checks that need them; then in the background after the case opens |
| `bc.set` sets the patch's own entry only | A condition given by a group or a pattern (`"(wall\|roof).*"`) isn't changed: the patch gets an entry of its own, which takes precedence; setting the group's entry needs `dict.set`-style editing of field files | A `bc.set` target for a group or pattern entry |
| A same-type `bc.set` can add or change keys, not remove them | Removing a key from a condition means giving the patch another type and back, or editing the file | A `remove` list in `bc.set` |
| Field files over the open limit (256 MB) are not edited | Their conditions can't be set here (they are listed without them already) | Rewrite the `boundaryField` part of a big file without reading its lists into numbers |
| One file changed outside since the case read it stops every save | `case.save` checks all files first and writes none when one changed on disk (also after an undo past a saved command), so unrelated edits wait until the case is opened again | Save the files that can be saved and list the conflicts |
| An edited field file is kept whole per change, for undo | Ten condition changes on a 500 MB field file hold ten copies until the undo history drops them | Store the edits as steps to replay, or cap undo by memory |
| The workflow covers the 3×3 pattern: snappyHexMesh and blockMesh regions in one case | Meshing chains spread over several cases (the Hong Kong project's extrusions, `sourceCase`) are checked step by step but not read into a workflow | Workflow steps for extrusion and for meshes taken from another case |
| `patch.create` with a box or a surface reads the region's boundary while the desktop app waits | About 3 s on the 16-million-cell air region of the HK project for one new patch (its points and boundary faces; no cells) | Read in the background (commands as jobs) |
| A surface, face set or workflow description that is a symbolic link is not replaced whole by a command | Repairing, scaling or replacing a surface linked to a shared STL is refused, and so is `workflow.import` over a linked `system/umcfWorkflow`: what the link points to stays as it is. Entry edits (`dict.set` on a linked description, `bc.set` on a linked field) are still saved through the link when it points inside the case; a link out of the case is refused at save, as for any file | A `replace` option that puts a file of its own in place of the link, or one that writes through it, with a backup of the file it points to |
| `case.save` checks for links before it writes anything, not right before each file | A file a command put whole that is turned into a link while the save runs is written through it | A write that doesn't follow a link at the path, checked by the case's file system right before the rename |
| `case.save` writes files but never deletes one | An undo after saving a command that made a file (a face set, a new `createPatchDict`) leaves that file in the case | Deleting the files a save made when an undo takes them away, with a backup |
| A script's effect is followed only for commands the check knows | After a Python helper or an unknown utility, the rest of that script is not checked for missing files | Declare a helper's outputs in the workflow |
| `dict.set` quotes a new key only when it starts with `(` | A new pattern key that doesn't (`"U.*"`) is written as a plain word, which OpenFOAM doesn't match as a pattern; existing quoted keys are found and kept | A parameter that marks a key as a pattern |
| Building-material coefficients are not checked for their keywords | Each entry of `buildingMaterials` reads its coefficients through its own dictionary (`VanGenuchtenCoeffs_`); a missing one is found only when the run starts | Map each material type's coefficient dictionary to its place in `transportProperties` |
| Keywords read under a condition or after the start are not required | A keyword read only in some branch, a loop or a later time step is found only when the run reaches it | Follow the conditions the solver can decide from the case (a flag in the same dictionary) |
| Field values are not checked | An `internalField` whose length doesn't match its mesh stops the solver when it reads the field. A NaN or infinite value in a binary field is read without a check (ASCII `nan` and `inf` already fail to read): it shows up only when the run's first calculation with it aborts on a floating-point exception (when those are trapped), or later as a diverging run. A negative `k` or `epsilon` is not an error: the turbulence model (`kEpsilon`, `realizableKE`) bounds it to a positive value when it is built and after every solve, and the run goes on with the changed values. The log says "bounding k" (and "bounding epsilon" in OpenFOAM-8); OpenFOAM-12 raises `epsilon` instead, to a floor set by `k`, with nothing logged | The length at open, for a `nonuniform` list: its header's count against the count of its field class (a `vol…Field` against `nCells`, a `surface…Field` against `nInternalFaces`, a `point…Field` against `nPoints`), all of which the `owner` header notes (read them all, not only the face counts). Without the note, `nInternalFaces` and `nPoints` come from the `neighbour` and `points` list headers; `nCells` needs the whole `owner` and `neighbour` files, so a volume field's length is checked only once the mesh is read whole (`mesh.check`, the mesh inside), and until then the case says it wasn't checked. The values: a check of their own that reads them as a stream when asked |
| The mesh quality check runs on one core, holds the whole mesh, and can't be cancelled | 14.6 s and 4.0 GB for the 16-million-cell air region of the HK project, during which the GUI would wait | Split the face loop over threads, as the reader does; read the files as a stream, without holding them whole (the memory work of the 3D scene); run it as a job with a cancel flag |
| Hidden regions and surfaces stay in memory, and regions are read in parallel | What the scene has read of a region or surface (with its BVH once it was picked in) is kept while it is hidden, until another case opens or `reload`: as much as showing everything at once. Up to one region per core is read at once, each holding its files: the five regions of the HK project peak at 2.8 GB (1.9 GB one after the other) | A memory budget for what is hidden, the least recently shown dropped first; readers started only while their files fit a memory budget |
| The 3D scene checks a mesh's `boundary` against the `owner` header only | The check finds a `boundary` whose patches don't tile the faces after the internal ones (they must start where the `owner` header's `nInternalFaces` says, when noted, and end at the `faces` file's count, which must match the header's `nFaces`; only the file's first 64 KB are read for it). It doesn't identify the mesh: a stale `boundary` with the same counts but other patch sizes passes and draws faces in the wrong patches. Without the note, where the internal faces end isn't checked either, so a `boundary` that tiles a different range of faces also passes | Warn when `boundary` is older than `faces` and `points` (OpenFOAM writes a mesh's files together; only a hint, as copying a case can change file times) |
| The 3D scene reads all of a region's points, and an uncompressed `faces` file whole | Drawing the 16-million-cell air region of the HK project takes 3.8 s and 1.8 GB the first time (5.6 s and 4.0 GB when the whole mesh was read). A compressed ASCII `faces` file (a `faceList`, as OpenFOAM writes ASCII faces) is read as a stream, its internal faces never held; an uncompressed or binary one is held whole while it is read | Keep only the points boundary faces use; read uncompressed and binary files as a stream too (a streaming read in `CaseFs`) |
| The desktop app's 3D view is drawn by the CPU renderer, on one core | Turning a mesh of millions of boundary faces is slow (the view draws at half resolution while it turns) | A wgpu viewport drawing the same scene; simplified display meshes built off the UI thread |
| The desktop app runs commands on the window's thread | Opening a large case or reading a big mesh freezes the window for seconds | Run commands as jobs with progress and a cancel flag |
| Command parameters are typed as JSON in the desktop app | Usable, not friendly | Forms from typed parameter descriptions in the registry |
| No control channel yet | `umcf-gui --control` (AGENTS.md §7) and `ui.screenshot` are not there; screenshots come from `--screenshot` | A JSON-lines server in `ui-egui` over the engine |
| Only STL surfaces are checked | OBJ, VTK and the other surface formats OpenFOAM reads in `constant/triSurface` are skipped by `geometry.check` | Readers for OBJ and VTK in `geom` |
| Transparent layers are sorted by triangle, the farthest first, after the edges and points | Where transparent triangles cross each other, or a long one lies over a short one, the nearer can be drawn first: a few pixels in the wrong order. A transparent surface also tints the wireframe edges and points behind it | Depth peeling, or a GPU viewport |
| A surface command keeps a copy of the file per change, for undo | Repairing a 500 MB surface ten times holds ten copies until the undo history (100 steps) drops them | Keep one copy per surface and store the repairs as steps to replay, or cap undo by memory |
| Standard OpenFOAM boundary-condition and model types are not in the catalog | A misspelt `zeroGradient` is not caught before the run; the condition card offers a short hand-written list of OpenFOAM's common types | Extend `xtask catalog` to the OpenFOAM sources the solver builds against |
