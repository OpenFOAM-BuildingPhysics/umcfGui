# Gaps

What umcfGui can't do yet, most important first. Work is picked from the top. A row is removed
in the same pull request that closes it.

## Next

The goal they lead to: a working case built in umcfGui from STL surfaces of its regions, with a
blockMesh background, its patches set up, its radiation and weather data set, and a mesh that can
be reset and made again. [What a case needs](case-requirements.md) is the specification, and
[the common workflow](common-workflow.md) the design rows 4–8 and 11 build.

## Known limits

| Limit | Effect | Possible fix |
|---|---|---|
| A patch in two groups takes each field from the group changed last that has it, not the one that set that field last | A display entry keeps the patch's mode and opacity together: two patch groups that share a patch hold neither the other, so when a group with an opacity of its own changes its mode after another group set its opacity, the patch is drawn with the changed group's opacity too (without one of its own, the patch keeps the other group's). A region, its groups and its patches are always right (what was set last wins) | Keep the order of each field (a mode-only and an opacity-only entry per layer) |
| A job's or container's memory limit is seen on Linux only | On Linux the memory budget stays within the cgroup v2 limits the app runs under (a SLURM job, a container). On Windows a job object's limit, and on macOS a container's or virtual machine's, are not looked for: the app plans with the memory the system says is free, which may be more than the job may use. `UMCF_MEMORY` sets it by hand | Read a Windows job object's limit (`QueryInformationJobObject`, through a crate) and what macOS offers for a process's limit |
| The field files are read whole before a check can judge them | The desktop app reads them after the case opens, in the background (the Hong Kong project at its latest time: its view shows at once, its fields take 2.6 s more, most of it decompressing the 600 MB `U` and `phi`); the CLI still reads them before the case opens | Show each field's conditions as it is read, not all at the end |
| `bc.set` sets the patch's own entry only | A condition given by a group or a pattern (`"(wall\|roof).*"`) isn't changed: the patch gets an entry of its own, which takes precedence; setting the group's entry needs `dict.set`-style editing of field files | A `bc.set` target for a group or pattern entry |
| A same-type `bc.set` can add or change keys, not remove them | Removing a key from a condition means giving the patch another type and back, or editing the file | A `remove` list in `bc.set` |
| Field files over the edit limit (256 MB) are not edited | Their conditions are shown and checked, but can't be set here | Rewrite the `boundaryField` part of a big file without reading its lists into numbers |
| One file changed outside since the case read it stops every save | `case.save` checks all files first and writes none when one changed on disk (also after an undo past a saved command), so unrelated edits wait until the case is opened again | Save the files that can be saved and list the conflicts |
| An edited field file is kept whole per change, for undo | Ten condition changes on a 500 MB field file hold ten copies until the undo history drops them | Store the edits as steps to replay, or cap undo by memory |
| The workflow covers the 3×3 pattern: snappyHexMesh and blockMesh regions in one case | Meshing chains spread over several cases (the Hong Kong project's extrusions, `sourceCase`) are checked step by step but not read into a workflow | Workflow steps for extrusion and for meshes taken from another case |
| `patch.create` with a box or a surface reads the region's boundary again for each new patch | About 3 s on the 16-million-cell air region of the HK project for one new patch (its points and boundary faces; no cells), behind the busy card | Take the boundary from the 3D scene, which has read it already |
| A surface, face set or workflow description that is a symbolic link is not replaced whole by a command | Repairing, scaling or replacing a surface linked to a shared STL is refused, and so is `workflow.import` over a linked `system/umcfWorkflow`: what the link points to stays as it is. Entry edits (`dict.set` on a linked description, `bc.set` on a linked field) are still saved through the link when it points inside the case; a link out of the case is refused at save, as for any file | A `replace` option that puts a file of its own in place of the link, or one that writes through it, with a backup of the file it points to |
| `case.save` checks for links before it writes anything, not right before each file | A file a command put whole that is turned into a link while the save runs is written through it | A write that doesn't follow a link at the path, checked by the case's file system right before the rename |
| `case.save` writes files but never deletes one | An undo after saving a command that made a file (a face set, a new `createPatchDict`) leaves that file in the case | Deleting the files a save made when an undo takes them away, with a backup |
| Tables a condition names by keyword are not checked | `CFDHAMsolidTemperatureTransferCoeff` and `…Interior` read an indoor temperature table, and `CFDHAMsolidMoistureTransferCoeff` a vapour pressure table, from files their entries name; a missing one stops the run at its first update | Read the conditions' file entries and check them as `case.table` does |
| A view factor key naming a patch group | `faceAgglomerate` matches it to the group's patches and then stops looking for the patch's own entry; the check counts the patches as covered by name or pattern only | Follow the groups as `faceAgglomerate` does |
| A script's effect is followed only for commands the check knows | After a Python helper or an unknown utility, the rest of that script is not checked for missing files | Declare a helper's outputs in the workflow |
| Building-material coefficients are not checked for their keywords | Each entry of `buildingMaterials` holds every coefficient its model reads, flat in its dictionary (`VanGenuchten`'s `wcap`, `n`: the catalog's `VanGenuchtenCoeffs_` is the model's copy of that dictionary); a missing one is found only when the run starts (`material.set` notes a name the catalog doesn't list) | Check each material's dictionary against the catalog's keywords of its model in `case.check` |
| Keywords read under a condition or after the start are not required | A keyword read only in some branch, a loop or a later time step is found only when the run reaches it | Follow the conditions the solver can decide from the case (a flag in the same dictionary) |
| Field values are not checked, and a field's length only against the `owner` header's note | A NaN or infinite value in a binary field, or a negative `k` or `epsilon`, may not be reported at all; in a mesh whose `owner` header has no sizes (written by hand or by an old tool), a field of the wrong length is found only when the solver reads it | The counts without the note: `nInternalFaces` and `nPoints` from the `neighbour` and `points` list headers, `nCells` once the mesh is read whole (`mesh.check`, the mesh inside). The values: a check of their own that reads them as a stream when asked |
| The mesh quality check runs on one core and holds the whole mesh | 14.6 s and 4.0 GB for the 16-million-cell air region of the HK project (a job in the desktop app, with a progress bar and *Cancel*) | Split the face loop over threads, as the reader does; read the files as a stream, without holding them whole (the memory work of the 3D scene) |
| The 3D scene checks a mesh's `boundary` against the `owner` header only | The check finds a `boundary` whose patches don't tile the faces after the internal ones (they must start where the `owner` header's `nInternalFaces` says, when noted, and end at the `faces` file's count, which must match the header's `nFaces`; only the file's first 64 KB are read for it). It doesn't identify the mesh: a stale `boundary` with the same counts but other patch sizes passes and draws faces in the wrong patches. Without the note, where the internal faces end isn't checked either, so a `boundary` that tiles a different range of faces also passes | Warn when `boundary` is older than `faces` and `points` (OpenFOAM writes a mesh's files together; only a hint, as copying a case can change file times) |
| The 3D scene holds every point of a mesh while it reads it, and reads binary mesh files whole | Drawing the 16-million-cell air region of the HK project takes 3.5 s and 0.87 GB the first time (all its 19.5 million points are read before the 1.9 million its boundary uses are kept; 5.6 s and 4.0 GB when the whole mesh was read). ASCII `points` and `faces` files with a header, compressed or not, are read as a stream (`CaseFs::reader`): the file isn't held, nor the text of the points or of the internal faces (only that of the boundary faces). A binary file is held whole while it is read, as are `faces`, `owner` and `neighbour` for the mesh quality check. The [memory budget](user-guide/scene.md#memory) limits how many such reads run at once | Read the boundary faces first and keep only their points as `points` streams by; read binary files, and the mesh check's `faces`, `owner` and `neighbour`, as a stream too |
| The grid jumps from one step to the next | When zooming changes the grid's step (1, 2, 5 times a power of ten), the new lines appear at once rather than fading in; the grid lies on z = 0 only, also in a side view where the ground is seen edge on; the origin's axes are one pixel wide | Fade between steps; a grid on the xz or yz plane in side views; wider lines (quads on the GPU, the same on the CPU) |
| A region's first wireframe or points layer is found on the window's thread | The edges and points wireframes and points draw (`Object::wire`) are found the first time a class shows them, on the window's thread, which waits (3.5 s for the Hong Kong project's five regions, on either view) | Find them as a job, as the scene is read |
| A file read whole stops on *Cancel* only once it is read | The status bar's bar fills where the job can tell how far it is: the field reading by files, the 3D view and the mesh check by the bytes of their files and their steps. *Cancel* stops a streamed read (ASCII `points` and `faces`, field files) within a megabyte, but a file read whole (binary, the mesh check's `faces`, `owner` and `neighbour`) only before the next one; other jobs show the megabytes read and seconds, the bar moving | Stream the files still read whole; steps for the other long jobs |
| A job that rebuilds the 3D scene copies it while the window shows it | During a job the window draws from a copy of the session that shares the scene; a queued pick after `patch.set` (the boundary changed) rebuilds the scene and, the old one still shared, copies it first: briefly twice the scene's memory on a big mesh | Objects shared one by one (`Arc` per object), so a rebuild takes those it keeps without copying |
| Command parameters are typed as JSON in the desktop app | Usable, not friendly | Forms from typed parameter descriptions in the registry |
| The GPU window's fallback to OpenGL is checked on Linux only | Without `--renderer`, the window opens on a hardware GPU; one that doesn't open is opened again on OpenGL, a second run of eframe's event loop (winit's run on demand, which Windows and macOS support too). The fallback was checked on Linux by forcing the GPU device to fail; on Windows and macOS it hasn't been run, and the CI doesn't open the window. A window that opens on the GPU but can't show (`ssh -X` to a machine with a GPU) may stop the app: `--renderer cpu` there | Run the forced failure on a Windows and a macOS machine; a CI job that opens the window under each system's display |
| No control channel yet | `umcf-gui --control` (AGENTS.md §7) and `ui.screenshot` are not there; screenshots come from `--screenshot` | A JSON-lines server in `ui-egui` over the engine |
| Only STL surfaces are checked | OBJ, VTK and the other surface formats OpenFOAM reads in `constant/triSurface` are skipped by `geometry.check` | Readers for OBJ and VTK in `geom` |
| Transparent layers are blended approximately | The nearest layer on each pixel is exact on both views (found first, blended last). Behind it, the CPU view sorts transparent triangles by their middles, the farthest first: where they cross, or a long one lies over a short one, the nearer can be drawn first (a few pixels). The GPU view doesn't sort those: layers of different colours over each other are mixed by weight, the nearer more, not in order. Both blend a transparent surface over the wireframe edges and points behind it, tinting them | Depth peeling (exact, a pass per layer) where few layers lie over each other |
| A surface command keeps a copy of the file per change, for undo | Repairing a 500 MB surface ten times holds ten copies until the undo history (100 steps) drops them | Keep one copy per surface and store the repairs as steps to replay, or cap undo by memory |
| Standard OpenFOAM boundary-condition and model types are not in the catalog | A misspelt `zeroGradient` is not caught before the run; the condition card offers a short hand-written list of OpenFOAM's common types | Extend `xtask catalog` to the OpenFOAM sources the solver builds against |
